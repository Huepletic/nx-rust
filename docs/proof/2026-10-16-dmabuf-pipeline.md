# dmabuf + пайплайн screencopy — итоги 2026-10-16

## Что сделано

1. **dmabuf-путь захвата** (`src/dma.rs`, `src/probes.rs`): dumb-буферы на
   `/dev/dri/card1` (CREATE_DUMB → PRIME_HANDLE_TO_FD → mmap), импорт через
   `zwp_linux_dmabuf_v1` **v3** (v4 фейлится требованием format+modifier
   advertised; провал импорта приходит неблокирующим created/failed).
2. **Пайплайн двух screencopy-запросов** (`NX_PIPE`): пара слотов, оба запроса
   висят pending до commit'а headless-выхода.
3. **Исправлен таймаут `timeout copy` в реальном стриме**: ready слота,
   прилетевший во время sleep'а пейсинга, диспатчится сразу
   (`event_queue.dispatch_pending` после sleep), а не ждёт квантования poll.
4. **Честный bench-режим `NX_SINK_READ=1`**: capturebench читает пиксели
   каждого кадра так же, как реальный стрим (см. «Выводы» — без этого флага
   bench врал про dmabuf).

## Ключевой вывод: dmabuf НЕ пригоден для реального стрима на этом GPU

Машинa: AMD APU (Wani/Radeon R6, `card1`, 0x1002:0x9874). mmap dumb-буфера
даёт **uncached/WC mapping** — CPU-чтение 3.48 МБ (кадр BGRA 1088x800)
стоит **~158 мс**.

| Прогон | params | copy/ready | sink | итог |
|---|---|---|---|---|
| capturebench dmabuf+pipe, БЕЗ чтения пикселей (утренний A/B) | 0.16–0.43 | 10.6–12.9 | 0.01–0.12 | **60 fps (фиктивно)** |
| capturebench dmabuf+pipe, `NX_SINK_READ=1` | 1.18 | 99.8 | 158.0 | **5.9 fps** |
| реальный стрим dmabuf+pipe (Moonlight) | 1.3–2.5 | 101–117 | 156–179 | **5.1–5.9 fps** |

Цифры bench-с-чтением и реального стрима **совпадают** — узкое место
воспроизведено: чтение dmabuf mmap в sink-кроужере. Утренний вердикт
«dmabuf+pipe — лучший» отменяется: bench-closure пиксели не читал, поэтому
60 fps измеряли не тот контур, который работает в стриме.

shm-mmap (memfd) читается из кэша: sink 2.0–2.7 мс.

## Реальный стрим: shm+pipe (текущий дефолт)

| Метрика | baseline (shm, seq) | сейчас (shm, pipe) |
|---|---|---|
| capture fps | 33–36 | **37.5–39.9** |
| params | 1.0–1.2 | 4.9–5.6 |
| copy/ready | 19.3–20.3 | 36.7–39.1 |
| sink (closure memcpy) | 7.2 (inline write_all) | 2.3–2.7 (writer-поток отдельно) |
| writer в ffmpeg | — | 37.8–39.0 fps, вытеснения единичны |

Потолок теперь — **насыщенный GPU**, а не цикл захвата:

- GPU busy **без стрима: 83 %** (в baseline-дне было 61–64 % — машина
  с тех пор сильнее загружена: load 7.4, два opencode, Chromium, AyuGram…);
- GPU busy со стримом: 75–80 %;
- темп commit'ов композитора под стримом ~38 Гц — fps равен commit-темпу;
- в изолированном bench (без ffmpeg) commits ~60 Гц → 60 fps достижимо
  только при запасе GPU.

## Судьба переключателей

- `NX_PATH`: дефолт теперь **shm**; `NX_PATH=dmabuf` — только осознанно
  (bench без чтения пикселей). Код dmabuf-пути сохранён (диагностика, PNG
  верификация ориентации — 0.23 % пикселей отличий от shm).
- `NX_PIPE`: дефолт **1** (2 слота). `NX_PIPE=0` — старая последовательная
  схема.
- `NX_WAIT`: poll-схема оставлена (C1 нейтрален).
- `NX_SHOT=<png>` — первый кадр в PNG (проверка ориентации/формата).
- `NX_SINK_READ=1` — bench читает пиксели как реальный стрим (**обязателен
  для честных замеров**).

## Опции для 60 fps (решение за заказчиком)

Потолок — GPU (idle 83 %). Варианты, не трогая запрещённое:

1. Принять ~38 fps как текущий результат (стабильно, latency не хуже
   baseline: decode на клиенте прежний класс).
2. A/B `-async_depth 1 → 2..3` в ffmpeg (меньше GPU-sync на кадр → возможно,
   commit-темп вырастет), но есть риск +задержки энкодера — мерить latency
   обязательно.
3. Снизить GPU-фон (закрыть часть приложений пользователя — только с его
   разрешения) и повторить замер.

Проверены все кандидататы read-only + одобренный DPM-A/B (с откатом):

|---|---|---|

| Низкий GPU-такт (DPM спит) | `pp_dpm_sclk` под стримом и bench | sclk 533–576 из 8 ступеней (макс 757); `gpu_busy` 78–87 % |
| Разгон снимает потолок | `power_dpm_force_performance_level=high` и ручной `pp_dpm_sclk=7` (оба — с откатом в auto) | **такт не поднялся** (hardware/power-cap платформы ThinkPad), fps не изменился (bench 52→52, стрим 39→39) |
| CPU-голодание Hyprland | /proc/842/stat в bench | **4 % CPU** — не bottleneck; в стриме ~44–50 % (рендер-работа) |
| Фон машины | load avg | bench 60 fps вечером при load 7.4; bench 51 fps ночью при load 4.2 — корреляции с CPU-фоном НЕТ |
| VCE-энкодер слаб | изолированный тест (baseline-док) | 148 fps testsrc2 — не слабое звено; его ВКЛАД = конкуренция за GPU (~12–14 fps commit-темпа) |

Диаграмма мониторов: eDP-1 1920x1080@60 + DP-2 1920x1080@60 + HEADLESS-4
1088x800@60, на каждом Chromium/AyuGram/foot. Три скан-аута + композитинг +
screencopy + VCE делят GPU, у которого нет запаса тактов (hardware-лимит
питания).

**Вывод: 60 fps на данном железе и текущей сессии недостижимы.** Потолок
измерен с трёх сторон: такты зафиксированы hardware-ом на ~70 % максимума,
GPU busy ~80 % без стрима, CPU-путь чист. Реальный потолок стрима —
**37.5–39.9 fps** (baseline 35): весь прирост программной части израсходован
на компенсацию регрессии фоновой нагрузки GPU. Для 60 fps нужно высвободить
GPU (мониторы/приложения — решение владельца сессии) или более мощное железо.

## Смерти стрима по таймауту copy — причина и починка (2026-10-17)

Три обрыва реального стрима по `capture: timeout copy кадр N` (N=62, 62780, 83410):

1. **Первая смерть (22:56)** — от DPM-покусов A/B: смена
   `power_dpm_force_performance_level` / `pp_dpm_sclk` даёт короткий GPU-stall,
   композитор не укладывается в 120-мс дедлайн copy-события.
2. **Вторая смерть (~00:07)** — без покусов: клиент был жив (аудио шло после
   смерти capture), kernel-лог чист (GPU-hang'ов нет), сессия не locked.
   Таймлайн совпал с `~/.config/hypr/hypridle.conf`: `timeout = 900` →
   `loginctl lock-session` → hyprlock. Лоченый экран (ext-session-lock)
   останавливает коммиты HEADLESS-4 → copy-событие не приходит → capture
   падает по собственному дедлайну.

Общий дефект кода: **любой одиночный стоп-кадр >120 мс рвал весь пайплайн.**

### Fix A — устойчивость capture-потока (src/probes.rs)

Таймаут/`failed` на этапах `buffer_params` (100 мс) и `copy` (120 мс) больше не
фатальны: слот отбрасывается, screencopy-frame уничтожается (без дестроя объекты
текутся), в следующей итерации кадр запрашивается заново. Фатал — только **20
отказов подряд** (≈несколько секунд мёртвого композитора). Прогресс в итерации
(любой слот дошёл до sink) сбрасывает счётчик.

### Fix B — idle-inhibit на время стрима (src/probes.rs, Cargo.toml)

capture_loop держит `zwp_idle_inhibit_manager_v1.create_inhibitor` на голом
`wl_surface`, пока идёт захват: композитор не шлёт idle-события → hypridle не
срабатывает → лок не включается. В wayland-protocols включена фича `unstable`.

Механика подтверждена исходником Hyprland v0.56.2,
`src/managers/input/IdleInhibitor.cpp`: поверхность без Hyprland-привязки →
`nonDesktop = true` → `PROTO::idle->setInhibit(true)` безусловно
("Assuming it's visible") — наш не-замапленный surface попадает в эту ветку.

Проверка: тестовый инстанс hypridle (30-с таймаут, безобидный `on-timeout`)
при живом стриме за 80 с не получил ни одного idle-события. Контрольный прогон
без стрима недействителен — оператор активен за машиной, idle не наступает ни
при каком условии; вердикт — по source-механике и практическому прогону.

Вердикт: стрим переживает лок сессии (во время лока — кадр-заморозка, после
разблокировки — продолжение) и короткие GPU-stall'ы. На время стрима авто-лок
не срабатывает — осознанный компромисс безопасности (одобрен оператором).
