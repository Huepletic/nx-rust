# Итерация C1: событийное ожидание вместо roundtrip+sleep — и блокер окружения

Дата: 2026-10-16, после baseline (`2026-10-16-fps-baseline.md`, 15:43).

## Что сделано (код)

- `src/probes.rs::wait_for()` — событийное ожидание событий wayland-сокета:
  `flush` → `dispatch_pending` → `poll(fd)` до события/дедлайна →
  `prepare_read().read()` → `dispatch_pending`. Вместо busy-`roundtrip`
  (write+read каждые ~0.1–0.5 мс) + `sleep 4мс` каждые 25 итераций в
  ожидании `copy_done` (латентность реакции до 4 мс на каждое ожидание).
- Заменены оба ожидания в `capture_loop`: `buffer_params` (дедлайн 100 мс)
  и `copy_done` (дедлайн 120 мс). Сборка `cargo build --release` чистая.
- Переключатель для честного A/B без пересборки:
  - `NX_WAIT=rt` — старая схема (roundtrip + sleep 4мс/25 для copy,
    без sleep для params — как было);
  - по умолчанию — poll-схема;
  - `NX_DBG=1` — построчный тайминг первых 12 ожиданий.

## Результат A/B (чередование rt/poll, одни и те же условия)

capturebench HEADLESS-4, 8–12 с, 4 прогона + контрольный «тихий» прогон:

| Режим | params, мс | copy/ready, мс | **сумма, мс** | fps |
|---|---|---|---|---|
| rt  (старый)  | 2.43 / 2.72 | 31.01 / 31.14 | 33.44 / 33.86 | 29.9 / 29.5 |
| poll (новый)  | 7.26 / 7.65 | 26.25 / 27.05 | 33.51 / 34.70 | 29.8 / 28.8 |
| rt  (тихий)   | 2.27 | 31.19 | 33.48 | 29.9 |
| poll (тихий)  | 7.45 | 26.44 | 33.90 | 29.5 |

Выводы:

1. **`params + copy` инвариантна ≈ 33.5 мс = ровно 2×16.67 мс** при любом
   режиме ожидания. Раздел params/copy смещается (poll ловит params раньше),
   но сумма — нет: всё квантовано на сетку композитора.
2. **C1 не даёт прироста FPS в текущем окружении** — клиентская скорость
   ожидания не важна, важен такт композитора. Poll-схема не хуже по fps,
   но бесконечно дешевле по CPU (нет spin-roundtrip) и логически чище —
   оставлена; её выигрыш (≤2–4 мс на квантование sleep) проявится только
   при 60-Гц такте композитора, сейчас он замаскирован.
3. Про poll-путь отладка `NX_DBG` показала: flush @0.01–0.05 мс,
   wake→read+dispatch → ready за 0.1–1 мс. Всё время (7–13 мс params,
   20–40 мс copy) — на стороне композитора.

## БЛОКЕР: окружение деградировало после baseline (15:43)

Симптомы (замеры 17:45–18:30):

| Метрика | baseline 15:43 | сейчас |

Что ПРОВЕРЕНО и исключено:

- наш код: A/B rt/poll даёт одинаковую сумму; сервер в покое (не стримит);
- память: Hyprland 0 major-faults/5с, swap как на baseline (1766 МБ), нет
  thrash'а;
- CPU: schedutil, 1.6–2.1 ГГц из 2.5, нет троттлинга, thermal зоны пусты;
- GPU: busy «залип» ~84 % (метрика подозрительна: константна и при
  нагрузке, и без; частота sclk 533 МГц — не троттлинг);
- второй клиент захвата: portal/pipewire screencast не активен, wayland-fd
  у xdg-desktop-portal и nxnode.bin нет;
- содержимое HEADLESS-4 статично (диф двух скриншотов 0.5 с = 131 пиксель,
  часы в баре);
- процессный состав почти не изменился с baseline (Chromium, AyuGram,
  2×opencode, foot, qs — все со вчерашнего дня). Новое после 15:43:
  tor (старт 18:07), второй chromium-рендерер (17:55) — оба позже первого
  провала (17:45).

Вывод: **потолок ~30 fps сейчас — композитор-сторона (глобально: все
выходы, цикл Hyprland вдвое реже), а не клиентский**. Это видно и самому
пользователю — его тачпад отстаёт на 20–90 мс. Воспроизводится «в тишине»
(после 60 с покоя) — нагрузка нашей сессии не причём.
