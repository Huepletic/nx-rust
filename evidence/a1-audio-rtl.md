# A1: аудио-тракт на планшет (opus/RTP)

Дата: 2026-10-19. Задача: «звук бежит вперёд картинки» → оказалось, звука на
планшет вообще нет: SDP без `m=audio`, ffmpeg без аудио-входа, :49002 только
приёмный. Внедрён аудио-конвейер по эталону Sunshine.

## Что сделано

- `src/stream/audio.rs`: PulseAudio-монитор дефолтного sink'а → libopus
  (48 кГц, стерео, CBR 96k, 5-мс фреймы, application=2050 restricted_lowdelay)
  → RTP на локальный UDP → форвард-поток клиенту. Пакет как у Sunshine
  (docs/research/stream.cpp:1874): header 0x80, PT=97, ssrc=0.
- Пир аудио учим из SS_PING клиента на :49002 (peer-learning как у видео).
- SDP DESCRIBE: `m=audio 0 RTP/AVP 97` + `a=rtpmap:97 opus/48000/2` +
  `a=fmtp:97 surround-params=21101`.
- ANNOUNCE: `x-nv-audio.surround.numChannels` (0 = клиент без звука) и
  `x-nv-aqos.packetDuration` (дефолт 5 мс).
- Синхронизация: `NX_AUDIO_DELAY_MS=80` (adelay) — видео-путь ~100 мс,
  аудио-путь ~20 мс.
- `audio_child` в PipelineHandle: stop() конвейера убивает и звук; wait() —
  против зомби.
- mDNS фикс (попутная поломка при рестарте): на wlan0 два IPv4 (.180 +
  secondary .181) → второй join_multicast_v4 по тому же интерфейсу = EADDRINUSE
  и смерть сервера. Теперь join по одному адресу на интерфейс.

## Найденные ловушки (проверено руками)

1. `-application restricted_lowdelay` эта версия ffmpeg не парсит
   («Undefined constant») — только число `2050`.
2. `prctl(PR_SET_PDEATHSIG)` умирает вместе с СОЗДАВШИМ ПОТОКОМ, а spawn шёл
   из RTSP-потока-обработчика → ffmpeg получал SIGKILL сразу после старта
   (лог: «audio: ffmpeg звука завершился», stderr пустой). Фикс: спавн в
   долгоживущем супервизор-потоке (audio-sup).

## Шифрование аудио (AES-128-CBC) и рывки

Доработки поверх первого замера (все проверены в живой сессии):

- **Шифрование**: пейлоад после 12-байтного RTP-заголовка шифруется
  AES-128-CBC (PKCS7). Ключ = `rikey` hex→16B, `avRiKeyId = rikeyid.parse::<i32>() as u32`,
  IV = BE32(key_id.wrapping_add(seq)) + 12 нулей, seq = host-order RTP seq.
  CBC вручную через `ecb::Encryptor<Aes128>`; юнит-тест `cbc_matches_openssl`.
- **Gate `AnnounceConfig::audio_encrypted()`**: `(feature_flags & 0x20) != 0 || (encryption_enabled & 4) != 0`.
  Клиент поддерживает дешифрование всегда (SdpGenerator.c:195, OR-условие) и
  сигнализирует `NVFF_AUDIO_ENCRYPTION (0x20)` в featureFlags.
- **Marker-фикс**: marker-бит очищается при форварде (`buf[1] &= 0x7f`) —
  клиент принимает RTP-аудио без marker.
- **Рывки**: PipeWire по умолчанию отдаёт pulse-демьюксу ~50-мс пачки →
  клиент видел интервалы 26-50 мс (рывки звука). Фикс: `-fragment_size 1024`
  для ffmpeg (замер `/tmp/rtp_gap_probe.py` до/после: было интервалы >26 мс,
  стало 0).
- **Гистограмма интервалов** форвардера (<7/7-12/13-25/26-50/>50 мс) каждые
  10 с в лог. Живая сессия: `1878/114/8/0/0` — >25 мс = 0.
- Сквозной тест: ANNOUNCE `featureFlags=167` → `audio_enc=true`; logcat
  0 decrypt-ошибок, 0 pending (в обычной сессии), 0 dropped;
  форвард 199.9 pkt/s, 121 kbps; AudioOut_1D `Standby: no`.

## Замер A/V-синхрона (метод и результат)

Метод: одно событие на хосте (вспышка tkinter через `hyprctl eval` на
HEADLESS-4 + тон 440 через pw-play). Планшет записывает screenrecord (видео)
и tinycap (микрофон, 48 кГц) в одном прогоне; хост-динамики мьютятся
(`pactl set-sink-mute`, monitor sink жив — проверено), чтобы микрофон слышал
ТОЛЬКО стрим-звук с динамиков планшета. Привязка часов хост↔планшет —
симметричный пинг `adb shell date` (C = планшет − хост).

Погрешности методики (проверено):

- **PTS screenrecord растянуты** ~2.8% относительно реального времени
  (интервалы событий vs PTS) → для абсолютного тайминга PTS непригодны,
  нужна поправка.
- **Финализация mp4** ~0.16-0.26 с после `--time-limit`; start_pts ≈
  mp4_end − dur − ~0.16.
- **`end_wav` нельзя снимать после `wait` screenrecord**: screenrecord живёт
  ~1.1 с дольше tinycap → артефакт «аудио-лаг +1.2 с» (это была ошибка
  таймстемпа, не лаг). Фикс: `(tinycap ...; date > end_wav) &`.
- **C дрейфует между прогонами** (+324 → +350 мс за час, NTP планшета), в
  пределах прогона стабилен ±5 мс → мерить C в том же прогоне.
- `pw-play` — единственный надёжный способ играть тон в реальном времени
  (`ffmpeg -f pulse` пишет 2.5x быстрее реального времени, звук обрезается
  буфером — проверено monitor-записью).
- screenrecord обязателен `--size` (иначе 0 байт); tinycap без WAV-заголовка
  бывает при обрыве — проверять RIFF.

Результат (поправленные времена, живая сессия):

- **Видео-путь** (вспышка на хосте → кадр на планшете): **+144 ± 8 мс**
  (3 события: +143/+136/+152).
- **Аудио-путь** (тон на хосте → звук динамиков планшета, изолированный
  прогон с мьютом): **+140 ± 15 мс**, из них pw-play старт ~30-50 мс и
  `NX_AUDIO_DELAY_MS=80` → сам тракт (capture+opus+сеть+AudioTrack)
  ~10-30 мс без adelay.
- **A/V-расхождение ≈ 0 мс** (оба пути ~140 мс) → `NX_AUDIO_DELAY_MS=80`
  компенсирует разницу пути ~100 мс против ~20 мс и синхрон удерживается.
  Крутить не потребовалось.

## Замер (живая сессия, планшет Moonlight)

```
audio: старт (pulse 'alsa_output.pci-0000_00_09.2.analog-stereo.monitor' → opus 96k/5ms → rtp://127.0.0.1:40192)
audio: peer 192.0.2.89:46969 (20B пинг)
audio: 186.6 pkt/s, 107 kbps (peer 192.0.2.89:46969, 5 мс/фрейм)
audio: 200.5 pkt/s, 115 kbps (peer 192.0.2.89:46969, 5 мс/фрейм)
audio: 199.4 pkt/s, 115 kbps (peer 192.0.2.89:46969, 5 мс/фрейм)
```

200 pkt/s = 1000 мс / 5 мс — ровно столько фреймов шлёт encoder, потерь на
форварде нет. 115 kbps CBR (96k payload + RTP/UDP/IP).

Видео при этом не просело: capture 60.0-60.1 fps, sync 3-6 мс (writer-лог).

## Итог

Замер A/V-синхрона подтвердил `NX_AUDIO_DELAY_MS=80` (расхождение ≈ 0 мс,
погрешность метода ±50 мс). Крутить не потребовалось. Шифрование аудио
AES-128-CBC включается автоматически по featureFlags=167; рывки устранены
`-fragment_size 1024`; >25-мс интервалов в живой сессии нет.
