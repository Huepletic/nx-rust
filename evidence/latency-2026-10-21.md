# Разбор задержки стрима nx-rust: что чинилось и что осталось

Дата: 2026-10-20 → 2026-10-21. Хост: nx-host (Arch, Hyprland 0.56.2).
Планшет-клиент: GSI Treble (Android 11), MTK mt6781, Magisk, com.limelight.

## Итог одной строкой

До правок: клиент 24–32 fps, постоянный «Waiting for IDR frame», кадры терялись,
HW-декодер не мог аллоцировать буферы. После правок: **сервер 60 fps без
вытесненных кадров, клиент 53–60 fps, 0% потерь в сети, сетевая задержка 1 мс,
декод 0 мс, измеренная сквозная задержка — медиана 44 мс**.

## 1. «Offline» у клиента: в ответе mDNS не было A-записи

Клиент (Moonlight) показывал ПК как «nx-host - Offline» и не подключался,
хотя `/serverinfo` отдавал 200 OK.

```
$ sudo tcpdump -i enp0s16u3 -n "udp port 5353"
22:30:47  192.168.8.89.5353 > 224.0.0.251.5353: SRV (QM)? _nvstream._tcp.local.
22:30:47  192.168.8.1.5353 > 224.0.0.251.5353: SRV nx-host.local.:48989,
                   TXT "version=1.9"            <-- A-записи НЕТ
```

В ответе были только SRV+TXT — клиент не знал адрес хоста и считал ПК офлайн.

**Правка** `src/mdns.rs`: в `build_response` PTR теперь добавляется на любой
вопрос по имени сервиса, а A-запись — всегда, когда в ответе что-то есть
(иначе клиент, спросивший только SRV/TXT, адрес не узнает).

```
22:30:47  192.168.8.1.5353 > 224.0.0.251.5353: SRV nx-host.local.:48989,
                   TXT "version=1.9", PTR nx-host._nvstream._tcp.local.,
                   A 192.168.8.1
```

## 2. Клиент не декодировал ни кадра: граллок отвергал бит usage 0x2000

```
E Gralloc4: buffer descriptor contains invalid usage bits 0x2000
E GraphicBufferAllocator: Failed to allocate (1088 x 800) layerCount 1
                           format 842094201 usage 402933: -22
E BufferQueueProducer: [SurfaceView - com.limelight/...Game#0]
                        dequeueBuffer: createGraphicBuffer failed
```

MTK-декодер просит у SurfaceView буферы с `GRALLOC_USAGE_HW_CAMERA_WRITE`
(0x2000); фреймворк AOSP этот бит режет и отдаёт -EINVAL. Декодер не отдал ни
одного кадра → клиент ронял кадры и просил IDR.

**Правка**: `tools/patch_libui_gralloc.py` — в `Gralloc4::Mapper`
(`validateBufferDescriptorInfo` и `createDescriptor`) маска
`0xFFFF00282400` → `0xFFFF00280400`, т.е. бит 0x2000 больше не запрещён.
Старая попытка патча (та же идея) била не в тот регистр: `w4` в
`allocateHelper` — это **layerCount**, а usage приходит в `w5`/`x5`.

Патч требует ребута планшета (Magisk-модуль `libui_gralloc_fix`).

## 3. «Waiting for IDR frame»: декодер отвергал ключевые кадры после первого

В `src/vaapi.rs` в slice-заголовок писался глобальный счётчик кадров:

```rust
b.put(frame_num, 8); // в IDR писалось 40, 80, 120…
```

H.264 (7.4.3) требует `frame_num = 0` в IDR и непрерывный счётчик P-кадров
после него. Декодер отвергал все IDR после первого — клиент вечно ждал
«Waiting for IDR frame» (519 сообщений за ~30 с).

**Правка**: `VaEncoder` получил поле `frame_num` (сбрасывается в 0 на каждом
IDR, дальше +1) и `force_idr`; в `encode_slot` битстрим-счётчики
(`frame_idx`, `pic_order_cnt_lsb`, `ref_pic_list0`, `top_field_order_cnt`)
переведены на него.

Плюс: запрос IDR от клиента (control `0x0302`) теперь реально форсирует
ключевой кадр — раньше он только логировался, и клиент ждал следующего
естественного IDR (до GOP=40 кадров ≈ 0.7 с). Флаг `StreamState::force_idr`
+ `VaEncoder::force_idr`.

Результат в логе клиента: `Waiting for IDR frame` 519 → 0,
`IDR frame request sent` 65 → 0.

## 4. Главный выигрыш: очередь вместо одного слота (29 → 60 fps)

Композитор отдаёт копии **пачками** (все слоты, готовые к одному commit'у,
приходят почти одновременно). Конвейер держал ровно один «готовый» кадр, и
всё, кроме первого в пачке, перезаписывалось:

```
writer: 29.0 fps в vaapi-энкодер (всего 23885), вытеснено 15575 (+11)
```

**Правка** `src/stream/pipeline.rs`: `ready` стал очередью `VecDeque`
(макс 4) с политикой «выбросить самый старый» — задержка не копится, но
энкодер переваривает всю пачку.

```
writer: 59.8 fps в vaapi-энкодер (всего 7447), вытеснено 3769 (+0)
capture: тайминг/кадр мс — params 0.59 | copy/ready 16.09 | всего 16.68 => 60.0 fps
```

## 5. Измерение сквозной задержки (объективно)

Метод: в кадре стрима горит live-время хоста с мс (`scripts/nx_clock_layer.py` —
layer-shell поверхность, насильно привязанная к монитору `HEADLESS-1`; экран
пользователя eDP-1 не трогаем), на планшете снимаем экран (raw, PNG-энкодинг
занимает 2.6 с против 0.17 с у raw) и читаем время из кадра.

Грабли, которые стоили времени:

| Проблема | Причина | Решение |
|---|---|---|
| замер ≈ −30 мс (невозможно) | смещение часов мерилось через **свежий** `adb shell`: установка соединения ~200 мс сдвигает исполнение команды к концу round-trip → смещение завышалось на ~55 мс | постоянная сессия `adb shell` (round-trip 10–30 мс), разброс смещения 8–12 мс |
| PNG-снимок 2.6 с | кодирование PNG на планшете | raw-формат: 0.17 с |
| кадр «из будущего» | SurfaceFlinger отдаёт последний отрендеренный клиентом буфер, а не отсканированный | калибровка на замороженных часах (SIGSTOP): контент статичен, цепочка сходится |

Калибровка (часы заморожены SIGSTOP, `F` = запечатанное в кадре локальное время
хоста) даёт поправку +11 мс; цепочка «время в кадре ↔ время съёма» сходится.

Результат (10 чистых выборок из 12):

**Медиана 44 мс** (при 8–82 мс по чистым выборкам), выбросы 404 и 5800 мс —
моменты, когда хост был загружен игрой пользователя (композитор отдавал
`copy/ready` до 114 мс).

Финальный прогон после ребута планшета и автовосстановления (12 выборок,

**Медиана 47 мс** — цель ≤50 мс достигнута (чистые выборки 5–76 мс).

Разница между прогонами (44 против 47 мс медианы) объясняется нагрузкой хоста:
`copy/ready` композитора 16 мс → 29 мс, когда у пользователя игра
(PlantsVsZombies через Wine) грузит композитор, — и медиана растёт теми же
~20 мс. **Задержка упирается в композитор хоста**, а не в сеть и не в кодек.

Из состава задержки (измерено по отдельности):

| Слагаемое | Величина | Источник |
|---|---|---|
| композитор: возраст кадра на копии | 16 мс (до 114 при нагрузке) | `capture: copy/ready` |
| кодирование VAAPI | 3.0–4.1 мс | `writer: работа ср` |
| сеть (RNDIS) | 1 мс | перф-оверлей клиента |
| декодирование | 0.00 мс | перф-оверлей клиента (HW-декод) |
| вывод на экран планшета | 0–17 мс | vsync 60 Гц |

## 6. Восстановление USB-канала: ребут ПЛАНШЕТА, а не USB-сброс с хоста

Рецепт пользователя (2026-10-21): «в будущее — фиксится ребутом ПЛАНШЕТА».
Это же подтвердилось: после ребута планшета гаджет поднимается заново, а
USBDEVFS_RESET с хоста дёргает гаджет и убивает xHCI (см.
`evidence/xhci-wedge-2026-10-20.md`).

В `watchdog.py` жёсткая ветка восстановления заменена:

* `reboot_tablet()` — `svc power reboot` через adb (функция adb — отдельная
  USB-функция ff/42/01, работает даже при мёртвом RNDIS-канале), ожидание
  возврата до 180 с;
* `tablet_gadget_fix()` — починка configfs на планшете
  (classic rndis.gs4 + ffs.adb → 0x2005; после ребута планшет поднимает
  только adb-only 0x201c, и RNDIS-функции нет);
* `restore_tablet_network()` — адрес rndis0 на планшете (192.168.8.89),
  fwmark-маршрут в таблице 97 (не в «таблице rndis0» — такой таблицы на
  Android 11 нет, `ip route ... table rndis0` даёт «table id value is invalid»),
  адрес хоста 192.168.8.1/24;
* `usb_reset()` оставлен только для ручной диагностики, в автопроцессе его
  больше нет.

## 7. Прочее

* `dnsmasq` на планшете крутился на 100% одного ядра (бесполезен: у него нет
  dhcp-range, он только слушает DNS) — убит, ядро освободилось.
* Односторонний батнс интерфейса хоста рвёт alt-setting RNDIS: после
  `ip link set enp0s16u3 down; up` пакеты идут только в одну сторону (TX=0,
  100% loss). Батнить надо обе стороны.
* Счётчик `errs` на rndis0 планшета всегда равен `packets` (особенность
  драйвера) — для гейта не годится, только для лога.
* IP хоста в RNDIS-подсети — 192.168.8.1: именно этот адрес Moonlight хранит
  в своей БД (`computers4.db`), менять его нельзя.
* Пользовательская игра (PlantsVsZombies через Wine) грузит композитор:
  `copy/ready` растёт с 16 до 30–114 мс, fps падает 60 → 47. Это влияет на
  задержку больше всего.

## 9. Что осталось за кадром

* Выбросы измерения (281/269 мс) не объяснены до конца — вопрос Q5 в ledger:
  SurfaceFlinger отдаёт последний отрендеренный буфер, а не отсканированный.
* Задержка растёт под нагрузкой композитора хоста (игра пользователя): с 16 до
  29–114 мс на `copy/ready`. Лечится только снижением нагрузки на композитор
  (или отдельным headless-рендером без общего композитора).
* `reboot_tablet()` в watchdog не отрабатывал вживую — ветка «ребут планшета»
  срабатывает, когда adb доступен, но RNDIS-канал мёртв; проверен сценарий
  «гаджет/адреса чиним сами» (п. 8), а ребут — следующий ручной прогон.
* Правки в репозитории не закоммичены (по состоянию на 2026-10-21).
