# Почему fps падал до 20–40 и что с этим сделано

Дата: 2026-10-21 (ночь). Хост: archpizdetc, Arch, 4 ядра, AMD Carrizo APU (iGPU),
Hyprland 0.56.2, мониторы eDP-1 1920x1080 и HEADLESS-1 1088x800 (scale 0.8).
Планшет-клиент: GSI Treble Android 11, com.limelight.

Задача пользователя: «60 fps только в простое, в остальное время 20–40».

## 0. Что оказалось не так с предыдущими измерениями

Мой замер CPU процесса через `awk '{print $14+$15}' /proc/<pid>/stat` читал
**majflt/cmajflt**, а не utime/stime. Из-за этого wireplumber «показывал» 460–3700%
CPU. Правильный замер (дельта utime+stime, индексы 11/12 после comm):
реально **~12%**. Часть «спиралей», которые я считал, была артефактом замера,
а реальный runaway (экземпляр wireplumber, намотавший 1 ч 46 мин CPU за 3 ч)
существовал и был настоящим.

## 1. Хост был в CPU-голоде (86% загрузки, PSI some = 75%)

Срез по всем процессам (дельты /proc/*/stat) в момент просадки fps:

| потребитель | CPU | чей это |
|---|---|---|
| wireplumber (PID 673) + его дубль (PID 4287) | ~63% + ~62% | два экземпляра: systemd --user и осиротевший (PPID=1) |
| Hyprland | 31–52% | композитор |
| AyuGram (Telegram) | 49% | пользовательское приложение |
| opencode ×3 | 56% | сессии агентов (моя + пользовательская) |
| ffmpeg (аудио nx-server) | 27% | наш, наследовал nice −10 от сервера |
| nx-server | 21% | наш |
| nx_audio_router.py | **70%** | мой скрипт, busy-loop |

**Как это бьёт по fps:** композитор (Hyprland) — тот, кто отдаёт нам
screencopy-кадры — не получал CPU, и цикл рендера растягивался с 16.7 мс до
26–45 мс. `copy/ready` = 26–45 мс → композитор коммитит 22–37 раз в секунду →
наш конвейер получает кадры пачками по 2 из одного коммита (второй — дубликат
содержимого) → реальная частота смены картинки 20–40 Гц, счётчик fps на клиенте
показывает больше.

### Что сделано

1. **Убит осиротевший дубль wireplumber** (PID 4287, PPID=1) — минус 0.62 ядра.
2. **Рестарт session manager'а** — у экземпляра был бесконечный retry по D-Bus
   `Unexpected reply 3 when releasing name org.freedesktop.ReserveDevice1.Audio0/Audio1`
   (журнал wireplumber). После рестарта — 12% CPU вместо 59%.
3. **Установлен `pipewire-libcamera`** — не хватало SPA-плагина для камер,
   wireplumber ругался `api.libcamera.enum.manager could not be loaded`.
4. **`scripts/nx_audio_router.py`: busy-loop устранён.** Поток событий Hyprland
   не давал уснуть в `recv()` → цикл крутился на 100% CPU. Добавлена пауза 50 мс
   (маршрутизация всё равно раз в 1 с).
5. **`src/stream/audio.rs`: ffmpeg-аудио получило nice +15** через `pre_exec`.
   Раньше наследовал nice −10 от сервера и отбирал CPU у композитора.
   Видео-путь важнее звука по задержке.
6. **watchdog**: правило самовосстановления — если wireplumber держит >40% CPU,
   перезапустить его (с правильным `DBUS_SESSION_BUS_ADDRESS`, иначе `systemctl
   --user` от системного юнита даёт rc=1).

### Результат в тех же условиях

```
writer: 59.9 fps … вытеснено +0     ср. vpp 0.66
capture: copy/ready 10–23 мс (было 26–45)
```

С 20–42 fps → 47–60 fps при работающей игре.

## 2. Предел, который остался: GPU

Замер «доля GPU» (выключил видеопоток на планшете, 30 с):

| состояние | gpu_busy_percent |
|---|---|
| без нашего видеопотока | 42–48% |
| с нашим видеопотоком | 76–95% |

Расклад по потребителям GPU:

* игра (wined3d, т.е. программная трансляция D3D9→GL) — ~45%;
* наш конвейер (screencopy-копия + VPP BGRX→NV12 + аппаратный H.264) — ~35–45%;
* композитор (два выхода) — единицы процентов.

Сумма ≈ 90% → композитор не может коммитить 60 раз в секунду, кадры приходят
пачками, половина — дубликаты. **Физический потолок на этом GPU**: игре нужно
≤45%, нам ≤35–45%.

Что можно сделать дальше (не сделано, требует решения владельца игры):

* ограничить fps игры (gamescope `-r 60` — пакет уже установлен, но сама игра
  падает с SEH-исключением, это чинится в другой сессии);
* перевести игру на DXVK (D3D9→Vulkan) — у wined3d и CPU, и GPU дороже в разы;
* уменьшить разрешение рендера игры.

Проверено, что gamescope-обёртка запускается, но не лечит падение игры
(`Exception frame is not in stack limits`).

## 3. Что ещё починено в watchdog

* Ребут ПЛАНШЕТА вместо USBDEVFS_RESET (рецепт пользователя): `USBDEVFS_RESET`
  с хоста убивал xHCI (см. `evidence/xhci-wedge-2026-10-20.md`).
* `tablet_gadget_fix()` — после ребута планшет поднимает adb-only (0x201c),
  RNDIS-функции нет; чиним configfs на планшете.
* `restore_tablet_network()` — адрес rndis0 192.168.8.89, fwmark-маршрут в
  таблице 97, адрес хоста 192.168.8.1/24, батнс обеих сторон.
* **Новое:** клиент на связи, а видеосессия не поднялась (после рестарта
  nx-server поднимается только аудио) — watchdog больше не считает это
  «стрима нет», а переподключает стрим (`client_connected()` + счётчик кадров).
  Проверено вживую: «СТРИМ НЕ ПОДНЯЛСЯ … переподключаю» → стрим поднялся.
* Правило «wireplumber в спирали → рестарт» (см. п. 1).

## 4. Убрано по просьбе пользователя

* Дебаг-баннер Moonlight (perf overlay): `checkbox_enable_perf_overlay=false`
  в `/data/data/com.limelight/shared_prefs/com.limelight_preferences.xml`
  (приложение перед правкой остановлено, чтоб не перезаписало префы).
* Часы в кадре (`scripts/nx_clock_layer.py`, layer-shell поверхность на
  HEADLESS-1) — процесс остановлен, слой `nxclock` на мониторе отсутствует.
  Скрипт остаётся в репозитории: он нужен для объективного замера задержки
  (`scripts/measure_latency.py`), запускается вручную и вешается только на
  HEADLESS-1, экран пользователя (eDP-1) не затрагивается.
